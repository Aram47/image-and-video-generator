# C++ Procedural People Image and Video Generator

## 1. Назначение

Создать приложение на C++, которое генерирует изображения и видео людей по текстовому описанию. Программа использует собственные процедурные алгоритмы и правила. Она не вызывает AI API и не использует предварительно обученные модели генерации изображений или видео.

Клиенты отправляют запросы серверу через TCP-сокет. Поле JSON `type` определяет режим:

- `image` — создать одно изображение;
- `video` — создать видео;
- `status` — получить состояние ранее принятой задачи.

Сервер разбирает prompt, строит структурированную сцену, генерирует персонажа и окружение, рендерит результат и возвращает состояние задачи и путь к результату.

## 2. Цели и ограничения

Первая версия должна уметь создавать стилизованных или простых 3D-персонажей с ограниченными вариантами внешности, одежды, поз и действий.

Программа сможет понимать только те слова и конструкции, которые явно реализованы в её парсере. Фотореализм и понимание произвольных описаний не входят в первоначальный объём. Неизвестные параметры нужно сообщать клиенту или обрабатывать согласно явно заданным правилам.

## 3. Архитектура

```text
Клиент
  │ TCP-сокет; JSON-сообщения, разделённые новой строкой
  ▼
C++ Generation Server
  ├── TCP-соединения и сборка сообщений
  ├── JSON-парсер и валидация запросов
  ├── Менеджер задач и очередь
  ├── Правиловый парсер prompts
  ├── Построитель описания сцены
  ├── Генератор персонажей и окружения
  ├── Система поз и анимации
  ├── Рендерер
  ├── Запись изображения и кодирование видео
  └── Хранение результатов и статусов задач
```

Сетевой слой должен проверять запросы и ставить их в очередь. Он не должен выполнять рендеринг напрямую.

## 4. Сокетный протокол

### Транспорт и формат сообщений

- Для первой версии использовать TCP.
- TCP передаёт поток байтов: один вызов `recv()` может получить неполное сообщение или несколько сообщений.
- Формат сообщений — NDJSON: UTF-8 JSON-объект, завершающийся символом новой строки `\n`.
- Сервер буферизует входящие байты до новой строки, затем разбирает одну JSON-строку и отправляет JSON-ответ с завершающим `\n`.
- Установить максимальный размер сообщения.
- Генерация выполняется асинхронно: сервер возвращает `job_id`, а клиент узнаёт о завершении отдельным запросом `status`.

### Запрос на изображение

```json
{
  "protocol_version": 1,
  "request_id": "client-request-001",
  "type": "image",
  "prompt": "A tall woman with curly red hair wearing a blue coat, standing on a city street at sunset",
  "options": {
    "width": 1024,
    "height": 1024,
    "seed": 12345,
    "style": "stylized_3d"
  }
}
```

### Запрос на видео

```json
{
  "protocol_version": 1,
  "request_id": "client-request-002",
  "type": "video",
  "prompt": "A young man in a green jacket walks through a park and waves at the camera",
  "options": {
    "width": 1280,
    "height": 720,
    "fps": 24,
    "duration_seconds": 4,
    "seed": 12345,
    "style": "stylized_3d",
    "action": "walk_and_wave"
  }
}
```

### Запрос состояния задачи

```json
{
  "protocol_version": 1,
  "request_id": "client-request-003",
  "type": "status",
  "job_id": "job-id-returned-by-server"
}
```

### Ответ о принятой задаче

```json
{
  "protocol_version": 1,
  "request_id": "client-request-001",
  "ok": true,
  "job_id": "job-identifier",
  "status": "queued"
}
```

### Ответ о завершённой задаче

```json
{
  "protocol_version": 1,
  "request_id": "client-request-001",
  "ok": true,
  "job_id": "job-identifier",
  "status": "completed",
  "result": {
    "media_type": "image",
    "path": "outputs/job-identifier.png"
  }
}
```

### Ответ с ошибкой

```json
{
  "protocol_version": 1,
  "request_id": "client-request-001",
  "ok": false,
  "error": {
    "code": "UNSUPPORTED_PROMPT_FEATURE",
    "message": "The requested feature 'wings' is not supported yet."
  }
}
```

### Выбор режима генерации

Выбирать обработчик по точному значению JSON-поля `type`. Не искать слова `image` или `video` в тексте prompt.

```text
image  → проверить ImageOptions → поставить ImageJob в очередь
video  → проверить VideoOptions → поставить VideoJob в очередь
status → проверить job_id       → вернуть JobStatus
другое → вернуть INVALID_REQUEST_TYPE
```

### Валидация

- Проверять `protocol_version`, `request_id` и `type`.
- Для запросов `image` и `video` требовать непустой `prompt` и ограничивать его длину.
- Проверять допустимые диапазоны размеров, FPS, длительности и количества кадров.
- Проверять тип и диапазон `seed`. Если seed не передан, создать его и вернуть в метаданных задачи.
- Возвращать структурированные ошибки для некорректного JSON, отсутствующих полей, неверных типов и значений вне диапазона.
- Не принимать путь для сохранения файла от клиента. Путь и имя файла формирует сервер.
- Отклонять поля, не относящиеся к выбранному типу задачи.

## 5. Разбор prompts без AI-модели

Парсер использует словарь, таблицы синонимов, простую грамматику и правила проверки. Это не AI-модель: он распознаёт только заранее реализованные варианты слов и фраз.

Пример prompt:

> A tall woman with curly red hair wearing a blue coat, standing on a city street at sunset.

Внутреннее представление:

```cpp
struct SceneSpec {
    CharacterSpec character;
    EnvironmentSpec environment;
    CameraSpec camera;
    LightingSpec lighting;
    std::vector<std::string> unsupportedTerms;
};
```

Пример разобранных атрибутов:

```text
character.gender_presentation = woman
character.height = tall
character.hair.color = red
character.hair.style = curly
character.outfit.outerwear = coat
character.outfit.primary_color = blue
environment.kind = city_street
lighting.time_of_day = sunset
```

Правила парсера:

- Нормализовать регистр, пунктуацию, пробелы и известные синонимы.
- Хранить значения в enum или ограниченных числовых диапазонах.
- Для отсутствующих параметров использовать предсказуемые значения по умолчанию.
- Сохранять неизвестные слова для диагностики.
- Не заявлять поддержку параметров, которые фактически не разобраны.
- Добавлять словарь и правила без изменений сетевого протокола.

## 6. Процедурная генерация людей

Хранить атрибуты персонажа в отдельных структурах:

- пропорции тела: рост, ширина плеч, пропорции туловища и конечностей, телосложение;
- лицо: форма головы, стили глаз, носа и рта, возможность добавить растительность на лице;
- внешность: поддерживаемые палитры кожи и волос, длина и форма волос;
- одежда: поддерживаемые типы одежды, цвета и варианты;
- поза: стояние, сидение, ходьба, махание рукой и другие реализованные позы;
- seed: управляемая генерация вариаций пропорций и деталей.

Для MVP использовать базовую стилизованную сетку с процедурными компонентами и скелет для позирования. Волосы и одежду сначала можно сделать упрощёнными сетками или слоями геометрии.

Разделить логику на этапы:

1. Выбор параметров персонажа.
2. Создание или деформация геометрии.
3. Назначение материалов и цветов.
4. Применение скелета и позы.
5. Размещение персонажа в сцене.

Одинаковые параметры и одинаковый seed должны давать повторяемый результат, насколько это возможно. Атрибуты, явно заданные в prompt, имеют приоритет над случайными вариациями.

## 7. Конвейер генерации изображения

1. Проверить запрос.
2. Преобразовать prompt в `SceneSpec`.
3. Создать геометрию персонажа и окружения.
4. Применить позу, камеру, освещение и материалы.
5. Отрендерить один кадр нужного размера.
6. Сохранить PNG в каталоге, сформированном сервером.
7. Отметить задачу как завершённую и вернуть данные результата.

Первоначальный формат изображения — PNG.

## 8. Конвейер генерации видео

Видео — это анимация процедурной сцены, а не независимо сгенерированные AI-кадры.

1. Проверить FPS, длительность, размер и максимальное количество кадров.
2. Разобрать prompt и определить поддерживаемое действие.
3. Создать персонажа со скелетом, окружение и состояние анимации.
4. Для каждого времени `t` вычислить позу и действие, затем отрендерить кадр.
5. Закодировать последовательность кадров в видеофайл.
6. Сохранить метаданные: seed, число кадров и формат.
7. Отметить задачу как завершённую и вернуть путь к результату.

Например, ходьба использует повторяемый цикл шагов и изменяет положение персонажа. Первая версия должна поддерживать небольшой список явно заданных действий.

Кодирование видео скрыть за отдельным интерфейсом, чтобы рендерер не зависел от конкретной реализации кодировщика. Первоначальный целевой формат — MP4.

## 10. Задачи и ошибки

Состояния задачи:

```text
received → validating → queued → running → completed
                                      └────→ failed
```

- Не выполнять рендеринг в потоке обработки сокета.
- Использовать ограниченную очередь и отдельные worker-потоки.
- На первом этапе ограничить параллельную генерацию одной задачей, если этого требуют память или GPU.
- Каждая задача сохраняет файлы в отдельный каталог.
- Поддержать запрос статуса по `job_id`.
- Отмену задач добавить после реализации базового жизненного цикла.

Начальные коды ошибок:

- `MALFORMED_JSON`
- `UNSUPPORTED_PROTOCOL_VERSION`
- `INVALID_REQUEST_TYPE`
- `MISSING_FIELD`
- `INVALID_FIELD_VALUE`
- `REQUEST_TOO_LARGE`
- `UNSUPPORTED_PROMPT_FEATURE`
- `UNSUPPORTED_ACTION`
- `RESOURCE_LIMIT_EXCEEDED`
- `JOB_NOT_FOUND`
- `RENDER_FAILED`
- `ENCODING_FAILED`
- `INTERNAL_ERROR`

Сообщения об ошибках должны помогать исправить запрос и не раскрывать stack trace, секреты или внутренние пути.

## 11. Безопасность и надёжность

- В разработке слушать только localhost.
- Перед доступом по сети добавить аутентификацию и TLS либо использовать доверенную приватную сеть.
- Ограничить размер запросов, длину prompts, размеры изображения, длительность видео, число кадров, очередь задач и объём хранения.
- Не подставлять пользовательский ввод напрямую в shell-команды или пути файлов.
- Создавать ID задач и пути к файлам на сервере.
- Обрабатывать отключение клиента без повреждения задач и утечек ресурсов.
- Логировать `request_id` и `job_id`, не записывая секреты.
- Удалять временные кадры после кодирования согласно настройкам хранения.

## 12. Требования к оборудованию

Разбор prompts и построение процедурной сцены могут работать на CPU. Рендеринг может выполняться на CPU или GPU — это зависит от выбранного рендерера и требуемой скорости.

GPU не обязателен для первого прототипа с низким разрешением, но полезен для больших изображений и видео, где нужно отрисовать много кадров. Не делать NVIDIA обязательным требованием продукта. Предусмотреть низкое разрешение для предварительного просмотра на ноутбуке.

## 13. Этапы разработки

1. **Сервер и протокол:** TCP, NDJSON, JSON-валидация, диспетчеризация `image`/`video`, структурированные ответы, запросы статуса и временное хранение задач.
2. **Грамматика prompts:** поддержка человека, роста, волос, одежды, фона, освещения и позы; обработка неизвестных слов.
3. **Статичный персонаж:** генерация одного стилизованного персонажа стоя и сохранение PNG.
4. **Варианты и сцены:** пропорции, волосы, одежда, фон, камера, свет и управляемая seed-вариация.
5. **Анимация и видео:** скелет, одно-два действия, отрисовка кадров и кодирование MP4.
6. **Клиент и подготовка к развёртыванию:** простой UI или CLI, аутентификация, TLS, постоянное хранение статусов, квоты и метрики.

## 14. Критерии готовности MVP

1. Клиент подключается к серверу и отправляет NDJSON-запрос на изображение.
2. Сервер распознаёт `type: "image"`, проверяет запрос и возвращает `job_id`.
3. Правиловый парсер преобразует поддерживаемые атрибуты человека в `SceneSpec`.
4. Процедурный генератор создаёт стилизованную сцену с человеком и сохраняет PNG.
5. Клиент запрашивает статус и получает данные результата.
6. Запрос `type: "video"` направляется в отдельный конвейер анимации и видео.
7. Видео-конвейер рендерит хотя бы одно поддерживаемое действие и создаёт MP4.
8. Некорректный JSON, отсутствующие поля, неподдерживаемый тип и недопустимые значения дают структурированные ошибки.
9. Фиксированный seed даёт повторяемые процедурные вариации.
10. Программа не вызывает AI-модель или внешний API генерации.

## 15. Пример полного запроса

```json
{"protocol_version":1,"request_id":"r-1","type":"image","prompt":"A short man with black hair wearing a yellow shirt, standing","options":{"width":512,"height":512,"seed":42,"style":"stylized_3d"}}
```

Сервер читает полную строку, проверяет запрос, создаёт задачу и возвращает `job_id`. Worker-поток разбирает поддерживаемые параметры, строит сцену, рендерит PNG и отмечает задачу завершённой. Запрос `status` возвращает итоговое состояние и расположение результата.

Для видео клиент отправляет `type: "video"` и параметры `fps`, `duration_seconds` и `action`. Сервер направляет запрос в конвейер анимации и кодирования.

## 16. Основное решение протокола

Использовать явное JSON-поле `type: "image"` или `type: "video"`. Не определять тип генерации по словам внутри prompt. Это делает протокол однозначным, расширяемым и удобным для C++-клиентов.
